## How v4 is served

```
                    lab runner (R2)                         Supabase / edge
 frames ──▶ ladder ──▶ model_runs ──▶ v4 activate ──▶ model_params {type: v4, serving, fallback}
                    └▶ R2 artifact ──┬─ offline ──▶ v4 serve (3×/day) ──▶ player_game_projections
                                     │                                   game_predictions
                                     │                                   v4_serve_features
                                     └─ trees ───▶ v4_models ──▶ live-poll (pitch, PA)
                                                               api (rest of game, live total)
```

- **Pregame markets** (`serving: offline`): `python -m modeling v4 serve`
  builds the frames with the day's slate as rows with no outcome yet
  (regular season or postseason; unposted lineups fall back to the team's
  last lineup), scores them with the frozen production fit and writes the
  same rows, keys and shapes game-predict always wrote. game-predict skips
  any key v4 covered and keeps its previous writer for the rest, so a failed
  publish degrades to the previous model, never to nothing.
- **In-game markets** (`serving: trees`): the fitted model is exported to
  JSON (`modeling/v4/export.py`) and scored in the edge functions
  (`_shared/v4.ts`), with live features built by `_shared/v4live.ts` from the
  play-by-play and the pregame snapshot in `v4_serve_features`.
- **Parity, pinned in CI:** `tests/fixtures/v4_trees_golden.json` (TypeScript
  scorer = Python, worst diff 4e-16) and `tests/fixtures/v4_walk_golden.json`
  (live state walk = the warehouse flattener the models were trained on).
- **Inputs a live scorer cannot compute are not features.** The v3 per-PA
  probabilities (`pa3_*`) are in the frames but not in any in-game market's
  feature list, so nothing is trained on an input that is missing when served.

## Operating it

```bash
# train / retrain (lab runner: commit modeling/lab/request.json on a claude/* branch)
python -m modeling v4 frames --grain player          # ~2.5 h (v3 pipeline + features)
python -m modeling v4 frames --grain micro           # pitch + count-state frames
python -m modeling v4 train player live pitch pa --record --publish

# put a market on the site (refuses a run the gate held)
python -m modeling v4 activate pitcher_k             # or a group: starter, game, ...
# take it off
select rollback_model('pitcher_k');                  -- service role

# keep it current: .github/workflows/v4-refresh.yml (06:15, 15:30, 18:15 ET)
python -m modeling v4 serve [--write-frames]
python -m modeling v4 score pitch pa --publish
```

**Edge function deploy.** The v4 code paths in `live-poll`, `game-predict`,
`api` and `backfill-predictions` are inert until a v4 row is active
(`legacyModels()` returns the active models unchanged, no spec loads). They
ship with the next deploy of the edge functions; activate a `trees` market
only after that deploy, or `live-poll` keeps scoring it with its fallback.

## Postseason

Every frame carries October games flagged `is_post`. The ladder scores them
with each season's model, the same model that scored that regular season,
and records `oos_metrics.postseason` beside the regular-season numbers; the
backfill carries them (`source = postseason`, and `production_postseason`
after training). Nothing is ever fitted on them, and selection never sees
them. The daily serve passes score postseason slates like any other.

Read-outs:

- **Starter markets are the clearest win.** Every one beats the incumbent on
  validation, on 2026 and in the postseason. The largest gains are in outs
  recorded (−7% RPS on validation, −13% on 2026) and hits allowed. By
  permutation importance on 2026 the lift comes from workload: days of rest,
  pitches thrown last start and season innings lead outs, hits and earned
  runs; for strikeouts and walks the v3 expected count still leads, with
  rest and the pitcher's Statcast-stuff features next (Model Lab · v4 →
  Features). For outs and earned runs the full-distribution multiclass GBM
  beat the negative-binomial GBM.
- **Game markets stay close to the incumbent.** For game totals a GLM on the
  new team-form and starter features beats it narrowly everywhere except the
  343 postseason games (within noise). The moneyline GLM ties the incumbent
  on validation (0.67533 vs 0.67523), so the gate **holds** it even though
  it is better on 2026: the gate wants a validation win, and production keeps
  the incumbent. Trees overfit both game markets; the ladder shows it.
- **Batter markets gain modestly and consistently:** 0.3–0.6% log loss on
  validation, smaller on 2026, against a strong v3 incumbent. Rest-of-game
  hits gains most (−2.6%): the in-game state (plate appearances so far,
  whether the starter is still in, his pitch count) is information the
  incumbent's "pregame rate over remaining PAs" ignores.
- **`game_total_live` first run: held, root-caused, retraining.** Every rung
  lost to the incumbent by ~5%. The market modelled the *final* total, so
  one dispersion had to cover a first-inning state and a ninth-inning one;
  the incumbent prices only the runs still to come, whose spread shrinks as
  outs run out. It now models `rest_runs` (final total minus the score), and
  the api adds the score back on. RPS is unchanged by that shift, so the
  numbers stay comparable. Lab job D reruns it; the first run's rows stay in
  `model_runs` and on the Iterations tab as the record of why.
- No market dropped a feature as uninformative; every chosen model is within
  the calibration band (1 ± 0.10).

## Known limits

- **Lineup timing.** A batter not in the projected (last) lineup gets a v4
  row only once lineups post and a serve pass runs (15:30, 18:15 ET);
  until then game-predict's previous model covers him.
- **In-game rows are approximations of their training grain.** Rest-of-game
  is trained before each of the batter's plate appearances and served at
  any moment; the live total is trained at half-inning starts and served
  mid-inning with the outs already made subtracted.
- **2016–2017 v3 columns are in-sample** for the v3 components fitted on
  seasons < 2018. Those rows are training-only; no reported number uses them.
- **2026 is partly spent** for `pa_outcome` feature choices (LAB.md); 2027 is
  the next clean test.
